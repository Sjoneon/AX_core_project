## 1. 후보와 비용 입력

### 1.1 `get_repair_candidates`의 구분

| 필드 | 내용 | 제한 |
| --- | --- | --- |
| `cause_candidates` | 기존 제조사 검색의 모델·품목·검토 필터를 통과한 원인/상황 최대 2개 | 원문 `causes`만 사용. 조치 설명·원본 JSON·QA 문자열을 원인으로 해석하지 않음. 현재 원인 확정이나 실행 승인이 아님 |
| `supported_candidates` | 현재 적용 가능한 원문 원인에 직접 명시된 부품 그룹, 명시적으로 검토한 오류 매핑, 고객이 정확한 부품 이름으로 문의한 비용 입력 | 원문 조치 설명의 부품명만으로 매핑하지 않음 |
| `USER_PART_REQUEST` | "메인 PCB 수리비"처럼 특정 그룹 비용을 문의한 경우 | 해당 부품의 고장 진단과 구분해 화면과 답변에 명시. 부정·지시문으로 선택한 부품은 제외. 일반 증상의 제조사 원인 설명을 가격 문의로 대체하지 않음 |
| `allowed_candidates` | 품목의 비용 그룹 허용 목록 | 목록 포함만으로 증상과의 연결 근거가 생기지 않음 |

### 1.2 비용 계산 조건

비용 도구는 아래 조건을 함께 확인합니다.

- `candidate_set_id`
- 허용 품목/후보
- 연결 근거
- 입력 확신도 0.5 이상
- 국내 같은 부품 사례 **3건 이상**

조건의 의미

- 3건: 이번 연결 경로의 보수적인 표시 정책이며 통계적 신뢰도나 고장 확정 기준이 아님
- 서버 정책의 0.8: 확인한 비용 입력 선택값이며 실제 고장 확률로 평가하지 않음
- 모델의 높은 확신도만으로 근거·사례 기준을 우회할 수 없음
- 대안: 최대 2개, 합산하지 않음

### 1.3 자료 부족과 후기 경로

- 자료 부족 시 반환: `NO_DATA`, 빈 `alternatives`, `missing_information`
- `REFERENCE` 후기 경로의 사용 조건
    - 정확한 등록 모델·오류에 해당하는 `VERIFIED` 유상 사례
    - 유효한 날짜, HTTPS 출처, 출장비 포함 조건
    - 고유 사례 3건 이상
- 제외: `VALIDATION`, 다른 모델, 중복 ID, 0원·소수 금액
- 실제 `repair-cases.json`: 계속 0건

### 1.4 실제 데이터의 가격 연결 예

| 입력/조건 | 결과 |
| --- | --- |
| 세탁기 "메인 PCB 수리비" | 고객이 문의한 W04 그룹, 국내 사례 4건. 평일 표 기준 124,569~230,145원, 중앙 169,319원·신뢰도 중간 |
| 위 문의 + 야간·휴일 7월 방문 | 표의 여름 야간 가산 10,000원만 적용. 중앙 179,319원. 다른 야간 가산과 중복하지 않음 |
| "배수펌프 수리비" | W01 그룹은 국내 사례 1건이므로 금액 없이 정보 부족 안내 |
| "배수가 안 돼요/OE, 수리비?" | 원인·부품 연결 근거가 부족하면 임의 펌프 가격을 제공하지 않음 |
| TR15WV5 "탈수할 때 흔들려요, 수리비?" | 적용 가능한 제조사 원인/상황 후보와 오류 표시 확인 질문. 부품·금액은 확정하지 않음 |

- 금액 출처: 패키지의 [parts.json][parts-json] 참고 범위
- 그룹의 가격 문의 예를 실제 고장 진단, 정확 SKU 부품 호환, 수리 견적, 개인별 무상 승인으로 표시하지 않음

## 2. 질문과 단계별 연결

### 2.1 추가 질문

- 일반 비용 문의의 부품·오류가 불명확하면 `REPAIR_DETAIL` 질문을 한 번 저장
    - 받는 응답: 표시 코드 또는 증상 설명, 표시 없음/모름
- 답변 뒤에도 근거가 없으면 같은 질문을 반복하지 않고 공식 점검으로 연결
- 답변에서 오류가 새로 파싱되어 진단 상태가 초기화돼도 원래 `COST` 문의는 유지

### 2.2 방문 조건

- 서버가 대화 상태에 저장하는 값: 정확한 부품 비용 문의, 방문 시간대·월
- 방문 월·시간대가 여러 개로 모호하면 추측하지 않음
- 입력이 없으면 표의 평일 기준과 월 미확인 고지를 사용하며, 현재 날짜를 방문 월로 가정하지 않음
- 제품 수정/변경 시 이 입력과 기존 후보 묶음 초기화

### 2.3 요청·상태별 호출

| 현재 요청·상태 | 호출/다음 안내 |
| --- | --- |
| 비용 문의 | 후보 조회 → 후보 묶음을 사용한 비용 조회 → 등록 제품 보증 조회 |
| 비용 근거 부족 + 추가 질문 대기 | 금액 없음·부족한 정보·질문. 응답 후 다시 계산 |
| 비용 근거 부족 + 질문 없음/응답 완료 | 위 조회 후 지역 센터·공식 접수 경로·상담 요약 |
| 승인 단계 모두 미해결 | 진단 결과 + 보증·센터·요약. 사유 `NOT_RESOLVED` |
| 실행 미승인 | 보증·센터·요약. 사유 `NOT_VERIFIED`, 수행 단계/실패를 생성하지 않음 |
| 검토 결과 조치 없음 | 보증·센터·요약. 사유 `NO_SELF_CARE` |
| 조건 미충족/모름 | 보증·센터·요약. 상태의 실제 조건 결과를 유지 |
| 서비스 문의/증상 특정 실패 | 확인한 제품·증상·보증·조치 결과로 공식 연결 안내 |
| 위험 의심/확정 | 기존 위험 안내 우선. 원인 부품·비용 조회 차단 |

- 자가조치 실패만으로 고장 부품을 정하지 않음
- 비용을 묻지 않은 실패 응답에서 금액을 자동 생성하지 않음
- 이후 비용 문의를 받으면 별도 후보·비용 조회 진행

## 3. 보증·센터·이력·한도

### 3.1 보증

- 계산 입력: 기존 등록 제품의 구입일·배송일·모델·증빙 등, `WarrantyService`로 계산
- 섞지 않는 기간: 품질보증(구입일 기준), 주요 부품 보증, 부품보유기간(제조일 기준)
- 구매일 수정으로 증빙이 미확인되면 보증 적용·만료일도 추가 확인으로 반환할 수 있음
- 이전 보증 결과나 이전 후보 묶음을 재사용하지 않음
- 무상 가능성을 금액 0원으로 바꾸지 않음

### 3.2 센터와 요약

- 센터 조회 순서: 등록 제품 배송지의 시·군·구 → 시·도 → 자료 없음, 공식 경로도 함께 반환
- 현재 시드 3곳을 전국 전체·거리순으로 표시하지 않음
- 요약 포함 항목: 모델, 증상, 현재 자가조치 상태, 수행 보고, 보증, 추가 확인 사항
- `PREPARED_ONLY`: 전송·예약·전화 발신은 수행하지 않음

### 3.3 호출 기록

- 비용/서비스의 필수 호출: 서버 정책으로 순서 결정
- 기록 구분: 기존 일반 상담에서 모델이 고른 도구는 `MODEL`, 보완 호출은 `POLICY_FALLBACK`
- 이 기록은 모델의 도구 선택 성공으로 계산하지 않음
- 최종 문단 구성: 기존 근거 검증 경로 사용

### 3.4 한도

- MCP 세션: 최대 5회, 도구당 2회, RPC 5초, 전체 20초
- 정책 보완도 같은 예산 사용
- 완료하지 못한 후속 조회: `tools.followup=PARTIAL`과 공식 경로 표시
- 단계 응답의 로컬 후속 조회도 같은 호출 수/전체 시간 상한 사용
- 상태·다음 안내·보증/센터/요약·도구 이력은 같은 트랜잭션으로 저장

## 4. 검증 범위

### 4.1 검사 환경

- 사용: 실제 FastMCP HTTP, Spring JWT/도구 API, H2 저장 이력, 실제 패키지의 비용 표/제조사 자료
- OpenAI: 기존 스크립트 응답 서버
- 평가하지 않은 것: 실제 모델의 도구 선택·상담 품질, 실물 수리 결과

### 4.2 검사 항목

- 실제 W04 부품 비용 문의의 범위·방문 가산·후보 묶음·등록 보증·이력
- 일반 증상 원인 후보, 질문·응답·오류 파싱 뒤 비용 문의 유지, 정보 부족 후 공식 연결
- 자가조치 모두 실패·조건 거절·미승인·증상 특정 실패와 후속 사유 구분
- 제품 수정 후 후보 버전 충돌·구입일/증빙에 따른 보증 재계산
- 부품 허용 목록만 있는 경우, 확신도 부족, 사례 0~2건, 잘못된 모델·미검증·중복 후기·0원, 문서/인자 주입 차단
- 실제 2회 제한 MCP 세션의 남은 보증 조회 표시, 위험 상태의 가격 조회 차단
- Python 계약의 새 연결 사유와 프론트엔드 후보·정보 부족 카드 표시 코드

### 4.3 최종 검사

- Java 286개 중 284개 통과, MySQL 마이그레이션 2개 건너뜀, JAR 빌드 성공
- Python 21개, 프론트엔드 10개·lint·build 통과
- discovery 계약 재생성
- 하지 않은 것: 원본 KB/구조화 자료·비용 데이터·승인 계획 확대, 운영 프로세스/DB 재시작
- 후속 범위: 일반 증상의 부품 매핑 확대, 검증된 수리 후기 확보, 부품보유기간 충돌 해소, 실제 모델 평가
