## 1. 분류 체계와 처리 순서

### 1.1 증상 코드

- 품목별 5개 증상 코드는 상담 상태용 코드
- 부품·고장 원인·자가조치 실행 승인을 뜻하지 않음

| 품목 | 증상 코드 |
| --- | --- |
| 세탁기 | `VIBRATION` 소음·진동, `DRAIN` 배수, `FILL` 급수, `POWER` 전원, `DOOR` 문 |
| 건조기 | `DRYING` 건조, `NOISE` 소음·진동, `POWER` 전원, `DOOR` 문, `ODOR` 냄새 |
| 냉장고·김치냉장고 | `COOLING` 냉장·냉동, `NOISE` 소음·진동, `FROST` 성에, `POWER` 전원, `ODOR` 냄새 |
| 식기세척기 | `WASHING` 세척, `DRYING` 건조, `DRAIN` 배수, `FILL` 급수, `POWER` 전원 |

### 1.2 의도와 서버 상태

- `intent`: `SYMPTOM`, `ERROR_CODE`, `SELF_CARE_REPLY`, `PRODUCT_REPLY`, `OUT_OF_SCOPE`, `OTHER`, `COST`, `WARRANTY`, `SERVICE`
- 서버가 저장하는 상태
    - 품목 불일치 확인 시: `CATEGORY_MISMATCH`
    - 증상을 끝내 특정하지 못한 경우: `UNCLASSIFIED`

### 1.3 처리 순서

1. 소유권·제품·오류 코드 확인, 기존 위험 검사 수행
2. 위험이 의심되거나 확정되면 기존 안전 경로를 먼저 실행(일반 증상 해석을 기다리지 않음)
3. 일반 상담: 품목·현재 문장·기존 질문·답·최근 이력·해당 모델의 승인 단계만 메시지 해석기에 전달
4. 허용 코드·신뢰도·JSON 형태 검사 후 서버의 질문·상태 전이 적용
5. 상태 버전과 소유권을 다시 검사해 저장, 질문이 있으면 질문 반환, 그 외에는 기존 MCP Agent 경로 실행
6. 사용자 문장·상담 답변·화면용 상태를 기존 대화 이력에 함께 저장

### 1.4 해석기 출력

- 일반 해석기 JSON 필드(5개): `intent`, `mentionedCategory`, `symptomCandidates`, `doneSteps`, `selfCareReply`
- 기존 오류 코드 추출과 위험 판단은 별도 경로 유지
- 원본 명세의 7개 필드를 하나의 AI 호출로 통합하거나 전체 9개 상담 상태를 다시 구현한 것으로 계산하지 않음

## 2. 질문과 실패 정책

### 2.1 증상 확정 기준

- 후보: 최대 3개, 현재 품목의 허용 코드만 유지
- 증상으로 저장하는 조건: 1순위 신뢰도 0.7 이상, 2순위와 0.15 이상 차이
- 불확실할 때: 후보 최대 3개와 `잘 모르겠어요` 표시
- 후보가 없을 때: 해당 품목의 증상 5개와 `잘 모르겠어요` 표시

### 2.2 질문 한도와 실패 처리

- 증상 질문: 한 번
- 질문 뒤에도 모르면 `UNCLASSIFIED`로 저장하고 공식 점검 안내, 같은 정보 부족에 질문을 계속 생성하지 않음
- 메시지 해석 시간: 최대 8초

| 상황 | 기록 | 동작 |
| --- | --- | --- |
| 시간 초과 | `TIMEOUT_FALLBACK` | 증상 선택으로 대체 |
| 오류·JSON 오류 | `INVALID_OR_ERROR_FALLBACK` | 증상 선택으로 대체 |

- 대체 시에도 확인된 기존 증상과 사실 답은 유지

### 2.3 선택 응답

- 서버 질문의 선택지와 정확히 일치하는 응답: `USER_SELECTION`으로 처리, AI를 호출하지 않음
- 선택 버튼: 기존 채팅 API로 문장 전송
- 과거 질문 버튼: 비활성화

### 2.4 개별 규칙

- 세탁기 진동에 발생 시점이 없으면 `VIBRATION_WHEN` 질문
    - 저장 값: `SPIN`, `WASH`, `ALWAYS`, `UNKNOWN`
    - 초기 문장에 탈수 시점이 있으면 다시 묻지 않음
    - 이해되지 않는 답은 한 번만 재질문
- 품목이 다르면 현재 품목을 자동 변경하지 않고 해당 품목의 새 상담 안내
    - 실제 지원 품목을 `OUT_OF_SCOPE`로 잘못 분류한 경우: 문장의 품목과 대조해 불일치로 처리
    - 대상 외 상담: 안내 후 종료
- 설명서의 증상을 인용하면서 현재 고장이 없다고 명시한 문장은 현재 증상으로 저장하지 않음
- 비용·보증·A/S 문의는 증상 선택을 강제로 거치지 않음

## 3. 저장 상태와 후속 응답

### 3.1 대화 상태 저장

- 위치: 기존 `consultation_context` JSON에 `dialogue` 추가
- 저장 내용: 의도, 언급 품목, 후보, 최초 증상 설명, 현재 질문, 증상 질문 횟수, 확인한 답, 해석 출처, 조치 결과
- 이전 JSON에 `dialogue`가 없으면 빈 기본값으로 읽음
- DB 열은 추가하지 않음

### 3.2 해석기에 전달하는 이력

- `ConversationService.dialogueHistory`: 최근 메시지 최대 12개를 시간 순서로 제공
    - 본문: 각 최대 1,200자
    - 포함하지 않는 것: 도구 원본, 제품 프로필, 자격증명
- 별도 전달: 마지막으로 표시된 승인 단계와 상태 버전
- Agent에 함께 전달: 등록 모델, 현재 상태
- 고객 문장과 이력은 지시가 아닌 데이터로 표시, 데이터 안의 `<`, `>` 이스케이프

### 3.3 후속 검색

- 검색의 서버 기본값과 자가검진의 내부 참조 검색: 저장된 증상 설명 사용
- `탈수할 때`, `그래도 안 돼요`처럼 짧은 후속 문장이 증상 설명을 덮어쓰지 않음
- 오류 코드가 있으면 기존 코드 검색 우선
- MCP `search_knowledge`의 명시적 `query` 입력 계약은 유지하고, Agent에도 저장된 증상으로 검색하도록 지시

### 3.4 승인된 완료 조치의 검증 경로

1. 현재 품목·등록 모델·증상/오류에 맞는 승인 단계의 ID나 안내 문구를 고객이 정확히 언급하고 수행했다고 명시한 경우
2. 바로 이전 답변에서 표시한 승인 단계의 상태 버전이 유효하고, 고객이 `그건 이미 확인했어요`, `그래도 안 돼요`, `이제 해결됐어요`처럼 그 단계의 결과를 명확히 답한 경우

- 완료 처리하지 않는 것: 유사한 다른 필터, 수행하지 않았다는 부정 문장, 승인되지 않은 단계 ID, 모델 변경 뒤의 과거 단계
- 당시 실행 자료는 0건이므로 실제 제품 상담에서 임의 단계를 만들지 않음
- 양성 완료 검증: 격리된 `TEST_ONLY` 단계로 수행

### 3.5 화면용 결과

- 위치: `tools.consultation`
- 포함 값: `intent`, `symptom_code`, 후보, 질문, 답, 완료 단계, 조치 결과, 종료 여부
- 서버 상담 상태 결과이며 MCP 도구나 도구 호출 이력 항목을 추가한 것이 아님
- MCP 9개 도구의 discovery 계약 유지

## 4. 검증과 재현

### 4.1 자동 검사

- 단위 검사: 허용 목록, 신뢰도, 출력 형태, 시간 초과, 기존 JSON 읽기, 질문 한도, 완료 조치의 정확한 대조
- 실제 FastMCP HTTP 통합 검사
    - 진동 입력 → 발생 시점 질문 → 답 저장 → 후속 검색·승인 미확인 안내 → 이력 조회
    - 잘못된 해석 → 증상 선택
    - 미분류, 품목 불일치, 대상 외
    - 소유권·버전 충돌
    - `TEST_ONLY` 완료·해결 저장
- 최종 자동 검증
    - Java 총 226개 중 224개 통과·2개 건너뜀, JAR 빌드 성공
    - Python MCP 20개 통과
    - 프론트엔드 10개 통과, lint·production build 성공
    - 건너뛴 2개: 별도 MySQL 실행 환경을 요구하는 `DatabaseMigrationTests`, 수행한 것으로 계산하지 않음
- 실제 메시지 해석 최종 38개의 최대 시간: 2,664ms(도구 호출·검색을 포함한 전체 상담 지연이 아님)

### 4.2 실제 모델 평가

- 구성(38개): 품목별 20개 증상, 비용·보증·A/S 문의, 부정·인용, 품목 불일치·대상 외, 정보 부족, 프롬프트 주입, 후속 응답·잘못된 완료 보고
- 최종 실행: 38/38
- 대체 경로로 우연히 기대 상태가 나온 경우는 AI 해석 성공으로 계산하지 않음

- backend에서 JDK 21 사용, 통합 검사 시 `HOMECARE_TEST_PYTHON` 지정


- 두 번째 명령: 기존 `.env`의 `OPENAI_API_KEY`·`OPENAI_MODEL`로 합성 평가 문장만 전송
