# B30 자료 사용과 냉장고 상담 답변 점검

확인일: 2026-10-15 (Asia/Seoul). 대상: 로컬 `main`의 `3b01ad6` 이후 작업본과 원격 반영본 `mcp_feature_integration`의 `66521d3`. 자료 버전: `B30-COST-V3-20261014-R5`.

## 판정

**B15·B16 파일만 읽고 있다는 주장은 사실이 아니다. 다만 B30 원본 전체가 서비스에 연결된 상태도 아니며, 자료를 찾더라도 답변에 필요한 정보가 충분히 전달되지 않는 문제가 있다.**

사용자가 제시한 `S836MEE022`의 “냉장고가 시원하지 않아요.” 사례는 단순히 B30으로 자료 이름을 바꾸거나 건수를 늘려 해결할 문제가 아니다. 원문 선택, 설명 필드의 답변 전달, 자가조치 승인, 등록 정보 연결, 보증 판정, 서비스 후속 호출과 화면 표시가 각각 영향을 준다. 현재 답변은 증상 이름을 반복한 뒤 확인 필요와 접수 안내를 길게 나열한다. 잘못된 실행 안내를 피한 것과 질문에 유용하게 답한 것은 별도의 기준이다.

확인 수량과 실제 Java 재현 결과는 [점검 증거 JSON](../benchmarks/manufacturer_data_usage_audit_20261015.json)에 저장했다. 과거 평가 결과를 이번 실행 결과로 재사용하지 않았다.

## 1. 실제 읽는 자료

```text
외부 B30 통합본 knowledge_effective_B30.jsonl: 1,659건
    ↓ 서비스로 가져온 부분집합 — 최초 변환 경로의 재현 코드 없음
backend/src/main/resources/homecare/knowledge.json: 1,542건
    ↓ structure_knowledge.py
homecare/knowledge-structured.json: 1,542건
    ↓ ToolDataCatalog → 적용 조건 필터 → KnowledgeRetriever
search_knowledge / get_diagnostic_plan
    ↓ AnswerContext → GroundedAnswerGenerator + 결과 카드
고객 답변과 저장 이력
```

[ToolDataCatalog](../../backend/src/main/java/com/project/backend/mcp/tool/ToolDataCatalog.java)는 패키지 내부 파일을 읽는다. 바탕화면 B30 폴더를 런타임에 직접 조회하거나, 새 원본 파일을 추가하면 자동 재수집하는 구조가 아니다. [구조화 생성기](../../backend/scripts/structure_knowledge.py)는 이미 가져온 `knowledge.json`을 투영한다. [비용 생성기](../../backend/scripts/build_homecare_data.py)는 비용 CSV를 변환하며 B30 지식 전체를 가져오지 않는다. [승인 계획 생성기](../../backend/scripts/build_approved_plans.py)는 B30 일부 원문을 검토해 특정 계획을 만드는 용도다.

현재 저장소에서는 B30 전체 → 서비스 지식의 최초 변환을 재현하는 생성기를 찾지 못했다. 따라서 누락은 ID 차집합으로 확인했지만, 당시 변환이 어떤 조건으로 각 행을 버렸는지까지 실행 코드로 확정하지는 못했다.

| 확인 항목 | 이번 결과 |
|---|---:|
| 바탕화면 B30 체크섬 목록의 파일 검증 | 58개 모두 일치 |
| 서비스 매니페스트의 파일 검증 | 9개 모두 일치 |
| B30 원본 / 서비스 지식 / 구조화 지식 | 1,659 / 1,542 / 1,542건 |
| 서비스 1,542건의 `text`를 파싱해 B30 전체 래퍼와 비교 | 불일치 0건 |
| 서비스에만 있는 사실 ID | 0건 |
| 원본 대비 서비스에 없는 사실 | 117건 |
| 그중 원본 품목이 `KIMCHI`인 사실 | 97건 |

전체 래퍼 비교에는 원문 `record`, 현재 QA, 최신 적용 보완, 유효 모델 목록, 절차 보완과 사용 정책을 포함했다. 파일의 JSON 공백 모양이 같은지를 비교한 것이 아니라 파싱한 내용 전체를 대조했다. 로컬·반영 작업 공간의 기존 JAR에도 동일한 지식 1,542건이 들어 있었다. 이는 운영 서버 프로세스가 해당 JAR을 실행하고 있다는 확인은 아니다.

## 2. B15·B16 ID가 나오는 이유

외부 `README_B30.md`는 B30을 B29 자료·검토·적용표를 함께 읽는 오프라인 통합본으로 설명한다. B30에서 새로운 제조사 사실을 추가하지 않았고, 원래 사실 ID도 유지한다. 따라서 **통합본 버전 B30과 사실 ID의 최초 배치 접두사는 서로 다르다.** `B30-` 사실 ID는 원본에도 없다.

| 원래 ID 접두사 | B30 원본 | 서비스 | 누락 |
|---|---:|---:|---:|
| B15 | 152 | 136 | 16 |
| B16 | 159 | 137 | 22 |
| B17 | 287 | 283 | 4 |
| B18 | 45 | 45 | 0 |
| B19 | 60 | 58 | 2 |
| B20 | 19 | 15 | 4 |

예를 들어 `B15-MFL71959119-warranty`의 최신 적용 보완에는 `B29-MFL71959119-core-warranty`가 연결돼 있다. B15·B16 ID를 가진 서비스 사실 중 최신 적용 보완이 있는 행도 17건이다. 현재 QA가 있는 행은 전체 원본 46건 중 서비스 36건, 최신 적용 보완은 45건 중 39건, 절차 보완 연결은 19건 중 19건이다. 원본 전체의 검토 수량을 서비스 전체 사용 수량으로 표시하면 안 된다.

`S836MEE022`의 냉각 약화에 맞는 현재 사실이 B15에 있는 것은 정상이다. 같은 모델의 B29 사실이 있다고 해서 다른 주제의 보증·서비스 지침을 냉각 원인의 근거로 우선하면 안 된다. [검색기](../../backend/src/main/java/com/project/backend/mcp/retrieval/KnowledgeRetriever.java)는 모델·품목·주제와 일치를 먼저 검사하며 배치 번호가 큰 자료를 우선하지 않는다. 점수와 모델 적용 상태까지 같으면 ID 순서로 정렬한다. 최신 의미 관계를 처리해야 하는 문제를 배치 번호 내림차순으로 해결하면 안 된다.

## 3. 검색을 실제 코드로 재현한 결과

현재 작업본과 원격 반영본을 각각 컴파일하고 `KnowledgeRetriever.lexical`을 직접 실행했다. 모델 API·벡터 검색·사용자 DB는 사용하지 않았다. 아래는 진단 사례이며 검색 품질 통과율이 아니다.

| 모델 / 질문 | 현재 작업본 결과 | 확인한 의미 |
|---|---|---|
| S836MEE022 / 냉장고가 시원하지 않아요. | B15의 `no_cooling`, `weak_cooling` | 사용자 답변에 나온 두 설명과 연결됨 |
| S836MEE022 / 냉장고 안에서 냄새가 나요. | B16의 `topic_46-000` | B16은 이 질문에는 맞는 냄새 자료 |
| FX24ENER / 탈수할 때 세탁기가 많이 흔들려요. | B17의 `topic_66-009` | 진동 조건 자료 사용 |
| RD21ESE / 배수가 안 돼요. | B29의 `drain-tank`, `hose-thaw`, `notice-1` | B29 자료도 실제 검색됨; 검색 성공이 조치 승인은 아님 |
| RD21ESE / 문이 안 닫혀요. | B29의 `notice-2` | 동일하게 후기 배치 사용 확인 |
| F12WVAR / 세탁 중 빨래 추가 방법이 궁금해요. | B28의 `add-laundry` | B28 자료도 실제 검색됨 |
| F12WVAR / 섬유유연제가 나오지 않아요. | 없음 | 해당 제목 계열 자료가 있어도 자연어 검색을 통과하지 못하는 범위가 있음 |
| M876GBB231 / 전체 용량은 몇 리터인가요? | 없음 | 제품 사양 레코드의 존재와 실제 응답 가능성을 구분해야 함 |

중요한 차이도 확인했다. **원격 `66521d3`의 어휘 검색은 사용자의 냉각 질문에 B16 냄새 문서를 반환했다.** 현재 작업본에 이미 있는 미커밋 `KnowledgeTextMatcher` 수정은 “냉장고 안”을 냉각 실패로 오인하지 않고, “정지·저하” 등 냉각 표현을 인식하도록 바꾼다. 작업본에서는 B15의 적절한 두 사실이 반환됐다. 이 수정은 앞선 1〜8단계 푸시에서 제외된 별도 변경이며 아직 원격 반영본에 없다. 이번 조사에서 새로 구현한 수정으로 계산하지 않는다.

실제 화면의 조회는 임베딩 상태·검색어 변환·설정에 따라 달라질 수 있다. 위 어휘 재현만으로 화면 전체가 같은 경로를 거쳤다고 확정하지 않는다. 배포할 때 원격 커밋·검색 모드·선택 문서 ID를 함께 확인해야 한다.

## 4. 제시된 냉장고 답변이 대부분 “확인 필요”인 이유

등록 화면에서 확인한 값은 `S836MEE022`, 구매일 `2026-05-05`, 제주 지역이다. 개인의 도로명·우편번호·상세 주소는 이 문서와 증거 파일에 복제하지 않았다.

### 4.1 설명할 정보가 있는데 최종 답변에서 빠진다

B30 원문과 서비스 래퍼의 두 사실은 서로 일치한다.

| 사실 | 원문 증상 | 원문의 `action_summary` | 구조화 결과 |
|---|---|---|---|
| `B15-MFL71401523-no_cooling` | 냉장·냉동 정지 | 전원 연결·전원 플러그 상태 확인 | `actionDescriptions`에 보존 |
| `B15-MFL71401523-weak_cooling` | 냉각 성능 저하 | 보관 온도·문 닫힘·식품 배치·주위 설치 환경 확인 | `actionDescriptions`에 보존 |

두 행의 `causes`는 비어 있다. [AnswerContext](../../backend/src/main/java/com/project/backend/mcp/agent/AnswerContext.java)는 증상·원인·일부 분기 조건만 답변 사실로 만들고 `actionDescriptions`를 사용하지 않는다. 그래서 증상 이름만 남고 “원인을 특정할 수 없어 공식 점검”이라는 문장이 반복된다. [구조화 생성기](../../backend/scripts/structure_knowledge.py)에서도 조치 설명은 검색 본문에 포함하지만 화면 본문에는 같은 방식으로 넣지 않는다.

이는 원문 자체가 없다는 뜻이 아니라 **검색용 자료 → 설명용 사실 사이의 전달·검토 범위가 좁은 문제**다. 그렇다고 모든 `action_summary`를 실행 안내로 풀면 안 된다. 설명 가능한 관찰 항목, 사용자 확인 질문, 전원 조작·청소·분해 등 실행 지시를 구분하고, 모델 조건과 출처를 붙인 검토된 설명 계약이 필요하다. 전원 관련 확인을 임의의 플러그 조작 지시로 바꾸지 않는다.

### 4.2 실행 승인 없음이 서비스 안내 전체를 불러온다

승인 계획은 현재 `TR15WV5 / UE / 세탁물 뭉침` 조건부 1건이다. S836MEE022의 실행 계획이 없어 `get_diagnostic_plan`은 `NOT_VERIFIED`를 반환한다. 이 상태는 “제품이 위험하다”, “모든 원인을 모른다”, “설명도 못 한다”와 같은 뜻이 아니다.

그러나 [RepairFollowupPolicy](../../backend/src/main/java/com/project/backend/mcp/agent/RepairFollowupPolicy.java)는 `NOT_VERIFIED`이면 보증·센터·전달 요약을 자동 조회한다. 사용자가 수리 접수를 요청하지 않아도 응답이 이 정보로 채워진다. [ConsultationMessage](../../frontend/src/components/ConsultationMessage.jsx)는 보증 결과가 있으면 전체 보증 카드를 표시하고, [ToolResults](../../frontend/src/components/ToolResults.jsx)는 각 도구 결과를 추가 표시한다. 채팅 본문의 반복을 줄여도 카드 전체는 남는다.

### 4.3 수정 전: 구매일이 있어도 기간 계산을 막는 조건 결합

이 절의 원인·합성 재현은 아래 구매일 기준 변경 **이전** 상태다. 증거 JSON도 당시 결과를 보존한다. 이후 사용자 요구에 따라 [구매일 기준 계산](warranty_implementation.md)을 구현하고 [별도 검수 기록](purchase_date_warranty_verification.md)으로 변경 후 결과를 확인한다.

[등록 화면](../../frontend/src/ProductDialog.jsx)과 [ProductRequest](../../backend/src/main/java/com/project/backend/product/ProductRequest.java)는 모델·구매일·주소를 받는다. 증빙 여부, 국내 신품·가정용 사용 여부, 주요 부품 유형을 이 경로에서 받지 않는다. 새 제품을 [UserProduct.update](../../backend/src/main/java/com/project/backend/product/UserProduct.java)로 저장하면 해당 보증 입력은 `null`이다.

수정 전 [WarrantyService.row](../../backend/src/main/java/com/project/backend/warranty/WarrantyService.java)는 구매일뿐 아니라 적용 조건과 증빙까지 참이어야 `expiresOn`을 계산했다. 하나라도 미확인이면 만료일·기간 상태·요금 상태가 함께 `UNKNOWN/CONFIRM_REQUIRED`로 남았다. 등록 구매일이 보이는 것과 보증 카드가 모두 미확인인 것이 동시에 발생한 이유다.

사용자 DB 대신 같은 등록 메서드로 합성 제품을 만들어 재현했다. 구매일은 보증 서비스까지 전달됐지만 조건 2개가 `null`인 상태에서는 만료일이 없었다. 동일 입력에 증빙·국내 가정용 조건을 명시적으로 참으로 주면 현재 정책 계산은 만료일 `2027-05-05`, `IN_WARRANTY`를 반환했다. 이는 이 고객의 조건을 실제 확인했다는 의미가 아니다.

사용자는 현재 구매일을 보증 시작일로 간주하도록 정했다. 이에 따라 **구매일 기준 기간 상태·만료일**과 **실제 무상 수리의 적용 조건**을 분리한다. 배송일이나 증빙 유무로 시작일을 바꾸거나 기간 계산을 막지 않는다. 해당 사례에서는 “등록 구매일 기준 제품 전체 보증기간 안입니다. 만료일은 2027-05-05입니다.”를 제공하고 무상 적용·비용 조건을 별도로 표시한다.

### 4.4 주소는 저장되지만 센터 검색용 지역으로 연결되지 않는다

신규 `UserProduct`의 `deliverySido`, `deliverySigungu`는 빈 문자열로 초기화된다. 일반 제품 등록은 `address`를 저장하지만 이 두 필드를 채우지 않는다. [센터 도구](../../backend/src/main/java/com/project/backend/mcp/tool/handler/FindServiceCentersTool.java)는 주소 문자열이 아닌 이 두 지역 필드로 검색한다. 합성 등록에서도 `address_present=true`인데 시·도·시·군·구가 모두 빈 값이었다.

화면에 주소가 있다고 해서 센터 도구가 제주를 검색했다고 볼 수 없다. 실제 저장 행이 기존 전용 API로 생성됐다면 지역 값이 있을 수도 있으므로 해당 고객 DB의 공란을 단정하지는 않는다. 다만 일반 등록 경로의 누락은 실제 코드와 합성 재현으로 확인했다.

여기에 `centers.json`이 대치·분당·북수원 3곳뿐이라는 별도 문제가 있다. 제주를 정상 전달해도 현재 목록에서는 결과가 없다. 두 문제를 모두 처리해야 하며 “검색 결과 없음”을 “제주에 A/S 센터가 없음”으로 표시하면 안 된다.

## 5. 누락 117건을 처리하는 기준

97건은 원본 `KIMCHI` 사실이다. 나머지 20건은 T6 경로 5건, B23 모델·설명서 연결 7건, B29 순위 참고 5건, 범위/공통 QA 3건이다. 상세 ID는 증거 JSON에 있다. `models.json`에는 김치냉장고 코드 5개가 `KIMCHI`로 존재하는 반면 지원 상담 enum은 4품목이다. 원본 분류를 무조건 일반 냉장고로 바꿔 가져오면 안 된다.

모든 누락 행을 고객 검색 문서로 넣는 것도 해결책이 아니다. 순위 참고나 QA 자체는 수리 설명이 아니며, 모델 연결과 경로는 해당 도메인의 참조 자료로 쓰는 편이 맞을 수 있다. 현재 서비스 래퍼 4건이 누락된 `B23-MAPPING-RG20WN/RG20VN`을 참조하는 점도 확인했다. 어떤 참조는 보조 이력인지 필수 실행 근거인지 구분해 복원·제외 이유를 기록해야 한다.

남은 범위:
- 기존 제품의 빈 지역은 주소 문자열을 쪼개 자동 보정하지 않는다. 마이페이지에서 주소 검색으로 다시 저장해야 한다.
- 관찰 질문은 냉장고 냉각 증상에만 있다.
- 확인 항목은 16개로 좁다. 확대는 검토 목록 추가로 한다.
- `centers.json`은 매니페스트 검증 대상이라 파일은 유지하되 조회에 쓰지 않는다.
- 행정구역 코드 저장은 DB 변경이 필요해 보류했다.
