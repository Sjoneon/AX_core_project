## 1. 운영 방향

### 1.1 기본안

- 냉장고·세탁기 등 고장 상담: **공식 출장 접수 연결을 기본으로 제공**
- 센터 찾기: 센터 방문이 필요한 경우에만 별도 제공
- 전국 센터를 직접 운영·동기화하지 않음

### 1.2 기존 경로를 교체하는 이유

- 교체 대상: 대치·분당·북수원 3곳이 담긴 `centers.json`을 전국 서비스 조회의 근거로 쓰는 경로
- 하지 않는 방식
    - 모든 센터를 소스 코드에 추가
    - 고객 요청마다 공식 웹사이트를 스크래핑
- 공식 API·데이터 공급 계약이 없는 현재, 운영 가능한 기본안은 공식 화면으로 인계하는 방식

### 1.3 공식 서비스 안내 확인

- LG [은평센터 안내][eunpyeong]와 [죽전센터 안내][jukjeon]: 냉장고·세탁기 등 대형 제품에 출장 서비스 안내
- 센터별 취급 품목도 다름
- 가까운 건물의 주소를 알려 주는 것과 해당 제품을 그곳으로 가져가 수리받을 수 있다는 것은 다름
- 건조기·식기세척기까지 동일한 내방 규칙을 추정하지 않고 해당 품목의 공식 서비스 안내 확인

### 1.4 공식 출장 예약과의 관계

- 공식 [출장 예약 화면][reservation]: 제품·증상·신청자·주소와 일정 확인 과정 제공
- HomeCare의 역할: 모델·증상·확인 이력을 요약하고 사용자를 이 경로로 연결
- 현재 앱을 예약 접수나 기사·방문 시간 배정 기능으로 표현하지 않음

## 2. 현재 문제

| 구분 | 현행 상태 | 실무상 문제 |
| --- | --- | --- |
| 데이터 범위 | 패키지 센터 3곳 | 전국 검색으로 해석되며 지역이 다르면 빈 결과가 발생 |
| 입력 연결 | 일반 제품 등록의 `address`와 센터 도구의 `deliverySido/deliverySigungu`가 분리 | 주소가 있어도 지역을 모르는 상태로 조회 |
| 결과 의미 | `fallback_level=NONE`, 빈 목록이어도 상태 `OK`와 "조회 완료" 카드 | 지역 미입력·자료 부족·실제 검색 결과 없음이 구분되지 않음 |

- 제주 사례: 현재 데이터에 제주 센터가 없고 일반 신규 등록의 지역 필드도 비어 있음
    - 센터 수를 늘리는 것만으로는 해결되지 않음
    - "등록 지역에 센터가 없습니다"라고 단정할 근거 없음

## 3. 1차 구현 범위

### 3.1 접수 채널과 센터 검색 분리

- 각각 명시하는 채널: 출장 접수, 전화 상담, 센터 방문 안내
- 냉각 문제를 처음 질문했을 때: 증상 설명과 필요한 확인 질문 먼저 제공
- 공식 출장 접수 버튼을 주된 행동으로 보여 주는 경우: 수리·접수 요청, 또는 적절한 설명 후에도 점검이 필요할 때
- 모든 턴에서 보증·센터·요약 카드를 자동으로 펼치지 않음

### 3.2 공식 연결 정보 관리

- 설정 자료로 관리: 공식 연결 URL, 대표 전화번호, 제조사, 확인일
    - URL과 전화번호를 설정에 두는 것은 센터 3곳을 전국 조회 결과처럼 쓰는 것과 다른 문제
- 연결 경로: 허용된 공식 호스트 사용, 주기적인 링크 상태 점검
- 공식 홈페이지 내부의 비공개 요청 경로나 임의의 주소·모델 쿼리 인자를 공개 API처럼 쓰지 않음

### 3.3 계약 개정

- 담당 도구: 현재 9개 MCP 도구 중 `find_service_centers`
- 입력·출력 계약과 소비 화면을 함께 개정
- 이름만 유지한 채 출장 예약 완료라는 전혀 다른 의미를 반환하지 않음
- 호환이 필요한 기존 결과와 새 응답은 계약 버전·조회 모드로 구분하고 저장 이력도 처리

### 3.4 목표 응답(설계안)

센터 데이터 공급이 없는 경우의 목표 응답입니다. 새 계약의 설계안이며 작성 당시 구현 값은 아닙니다.

```json
{
  "status": "EXTERNAL_LOOKUP_REQUIRED",
  "data": {
    "service_mode": "ON_SITE",
    "directory_status": "NOT_INTEGRATED",
    "region_status": "KNOWN",
    "region": {"sido": "제주", "sigungu": "제주시"},
    "centers": [],
    "channels": {
      "onsite_booking_url": "https://www.lge.co.kr/support/service-engineer-reservation",
      "center_finder_url": "https://www.lge.co.kr/support/find-service-center",
      "phone": "1544-7777"
    },
    "booking_status": "NOT_SUBMITTED"
  }
}
```

- 화면 문구: "센터 조회 완료, 등록된 센터 없음"이 아니라 "냉장고 점검은 LG 공식 출장 접수로 이어갈 수 있습니다"와 공식 연결 버튼
- 센터 방문을 원하면 공식 센터 찾기를 별도로 엶
- 하지 않는 것: 주소를 공식 페이지에 자동 전송, 사용자 대신 접수, 미지원 자동 입력 약속
- 제공하는 것: 모델·증상 요약 복사

### 3.5 등록 주소 연결

- 주소 검색 결과에서 받는 값: 기본 주소·상세 주소, 시·도·시·군·구의 정규화된 값, 가능하면 행정구역 식별자
- 도로명 주소 문자열과 정규 지역 정보를 같은 등록 경로로 저장
- 수동 입력·기존 데이터에서 지역을 확정할 수 없으면 `REGION_REQUIRED`로 구분해 한 번 확인
- 결정 필요: 기존 `deliverySido/deliverySigungu` 유지 또는 새 지역 필드 사용(DB 변경 범위와 함께 결정)
- 화면의 "설치 주소"와 조회에 쓰는 "배송 지역"의 의미 통일 필요
- 주소 문자열을 임의로 쪼개 빈 필드를 채우고 성공 처리하지 않음
- 기존 행의 보정: 확인 가능한 주소 변환과 별도 마이그레이션·검증으로 수행

### 3.6 센터 3곳 자료의 역할 제한

- 운영 검색에서 `centers.json`의 3곳을 기본 조회 소스로 쓰지 않음, 필요하면 테스트 고정 자료로 분리
- 파일만 삭제하지 않는 이유: `ToolDataCatalog`의 필수 파일·매니페스트·해시 검사·센터 도구·계약·화면·회귀 테스트가 이 파일에 연결
- 다른 제조사로 확장할 때도 채널 제공자와 센터 디렉터리 제공자 분리

## 4. 자체 센터 목록이 제품 요구사항이 된다면

### 4.1 데이터 공급 경로

- 앱 안에서 센터 이름·위치·취급 품목을 보여 주는 것이 필수라면, 공식 제휴 API 또는 운영 가능한 승인된 데이터 공급 경로를 먼저 확보
- 확인 결과: 공식 페이지 확인과 검색에서 이 앱이 사용할 공개 센터 조회 API 계약은 확인하지 못함(존재하지 않는다는 단정은 아님)
- 웹 화면이 내부적으로 JSON을 받는다는 이유만으로 연동 계약이 확보된 것으로 보지 않음

### 4.2 조회 방식

- 공급 경로 확보 후 결정: **지역별 소량 호출만 할지, 제공 목록을 주기적으로 동기화할지**(제공자의 계약·갱신 정책 기준)
- 전체 목록을 안정적으로 받을 수 있다면 백그라운드 동기화한 자체 DB 조회가 매 채팅마다 전국을 다시 수집하는 것보다 적합
- 이 경우 전국 센터는 코드 안의 상수가 아닌 운영 데이터

### 4.3 필수 관리 항목

- 제공자·외부 센터 ID·공식 상세 URL, 정규 지역, 주소·좌표, 서비스 방식과 취급 품목, 운영 상태, 출처 확인일
- `source_updated_at`, `fetched_at`, 마지막 성공 동기화와 실패 상태
    - 데이터 갱신 주기는 공급 조건을 확인해 정하고, 사용자에게 최근 확인일 표시
- 검증 후 전체 스냅샷 교체 또는 변경분 적용
    - 일부 수집 실패·행 수 급감으로 전국 목록을 빈 목록으로 덮어쓰지 않음
    - 이전 정상본 보존과 되돌리기 경로
- 삭제·이전·휴무·운영시간 변경 반영
    - 구분할 상태: 조회 실패, 자료 만료, 지역 미확인, 유효한 검색의 결과 없음
- 조회 기준: 지역·제품·서비스 방식
    - 좌표와 거리 계산을 구현한 경우에만 거리순이라고 표시
    - 가장 가까운 센터가 출장 배정 담당 센터라고 추정하지 않음
- 제공자 인증정보는 서버에서 관리
    - 외부 오류: 제한된 재시도·타임아웃, 이전 자료의 사용 여부·확인 시각 또는 공식 조회 연결 반환
    - 공급 API가 없을 때 계속 실패하는 호출을 고객 요청마다 반복하지 않음

### 4.4 캐시와 예약 시간

- 검색 요청별 결과의 짧은 캐시: 공급 경로가 확보된 뒤의 최적화
- 캐시만으로 원천 데이터의 범위·이용 가능성·갱신 문제가 해결되지 않음
- 공식 예약 가능 시간은 단순 센터 주소 정보와 다르므로, 별도 예약 연동 계약 없이 계산·확정하지 않음

## 5. 완료 기준

| 검증 사례 | 기대 결과 |
| --- | --- |
| S836MEE022·제주·냉각 약화, 첫 질문 | 질문에 대한 설명·필요한 확인 질문 우선. 센터가 없다는 단정과 불필요한 전체 카드 나열 없음 |
| 같은 제품의 출장 수리 요청 | 공식 출장 접수 연결·모델/증상 요약·아직 접수하지 않았음 표시 |
| 수도권 신규 등록과 제주 신규 등록 | 설치 주소와 구조화 지역이 함께 저장되고 수정 후에도 일치 |
| 주소는 있으나 기존 지역 필드 공란 | 필요 시 지역 확인. 빈 지역으로 검색한 뒤 조회 완료로 처리하지 않음 |
| 공급 경로 미연동 / 외부 장애 / 결과 없음 | 서로 다른 응답과 고객 문구. 3개 고정 센터로 조용히 대체하지 않음 |
| 자체 디렉터리가 도입된 경우 | 전국 범위·취급 품목·최근 갱신·장애 복구 검증. 제주를 포함한 수도권 외 사례 검사 |
| 기존 저장 상담 재조회 | 과거 센터 결과를 당시 안내로 표시. 최신 영업·예약 가능 상태로 오인시키지 않음 |

- 1차 구현에서 반영한 것: 출장 연결, 주소 연결, 응답 상태(DB 스키마는 변경하지 않음)
- 진행 순서: 출장 연결과 주소 연결·응답 상태 교정 → 자체 센터 디렉터리는 사업상 필요와 데이터 공급이 확인되면 별도 작업
