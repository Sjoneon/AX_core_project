# HomeCare AI 제품 데이터 활용성 분석·검수 보고서

작성일: 2026-10-13, Asia/Seoul · 버전: 1.0

대상 주제: **세탁기·건조기·냉장고(김치냉장고 포함)·식기세척기의 수리 전 제품 확인, 안전한 자가검진, 보증·부품·예상 수리비·공식 A/S 안내.**

검수 결론은 다음과 같다. 제품 코드·설명서 연결·출처·적용 조건은 이 프로젝트의 핵심 자산으로 활용할 수 있다. 오류·증상·안전·보증·유지보수 원문도 유용하지만, 모델과 절차 조건을 검증한 뒤 용도별로 사용해야 한다. 현재 자료만으로 정확한 교체 부품, 국내 수리 총액, 개인별 무상 수리 또는 실행 가능한 모든 자가조치를 확정할 수는 없다.

**현재 연결에서 우선 보완할 사항은 김치냉장고 원문 97건의 누락, 제외 모델이 검색 후보에 포함되는 문제, 공통 범위의 잘못된 모델 코드 표현, 승인된 자가검진·증상-부품 매핑의 부재다.** 원본 자료의 활용 가능성과 현재 코드의 구현 상태를 구분해 아래에 정리했다.

이번 요청에서는 분석·정적 검수와 보고서 작성만 수행했다. 애플리케이션 코드·운영 자료·Drive 원본은 수정하지 않았다. 발견한 문제의 수정 완료나 실제 모델의 답변 정확도를 주장하지 않는다.

### 1.2 검수의 수준

전체 레코드에 대해 JSON 파싱, ID 일치·중복, URL 형식, 기준일 형식, 모델 참조, 현재 파일 해시, 원본 대비 누락 ID, 사용 제한 플래그와 검색 메타데이터를 확인했다. 주요 원문·검토 조건은 사실 ID별로 상세히 읽고, 현재 검색 필터와 점수 계산을 오프라인에서 재현했다.

공식 부품 페이지 2곳은 이번에 열어 부품명·표시 가격·실제 SKU 목록을 표본 확인했다. 설명서 주제 URL 2곳은 웹 도구에서 본문을 가져오지 못했으므로, 해당 절차의 판정은 보관된 B30 원문과 검토 기록을 근거로 했다. 25개 설명서 전체의 그림·설치 조건을 현장에서 다시 검증하거나 실제 제품을 조작한 것은 아니다.

이 보고서의 '사용 가능'은 아래에 명시한 용도로 활용할 수 있다는 뜻이다. 제조사 엔지니어의 실행 승인이나 모든 데이터의 무조건적인 정확성을 뜻하지 않는다. 원본 문서의 재개·수집 지시문도 이번 사용자 요청과 구분해 자료로만 읽었다.

## 2. 데이터의 실제 규모와 품질

### 2.1 제품 목록과 식별

| 품목/하위 유형 | 대표 모델 | 판매 코드 | 앱의 품목 |
|---|---:|---:|---|
| 세탁기 | 14 | 18 | `WASHER` |
| 건조기 | 5 | 14 | `DRYER` |
| 일반 냉장고 | 8 | 8 | `REFRIGERATOR` |
| 김치냉장고 | 5 | 5 | `REFRIGERATOR`, 하위 유형은 별도 보존 |
| 식기세척기 | 6 | 7 | `DISHWASHER` |
| 합계 | 38 | 52 | 4품목 |

원본 제품 52개와 판매 코드 조회표 52개의 연결에서 누락을 찾지 못했다. 대표 모델 참조와 설명서 ID 참조도 해석 가능했다. 색상 등 대표 모델과 별도로 등록된 판매 코드는 14개다.

반면 `products_B30.json`의 `specification_evidence`가 비어 있는 코드는 10개다: `F24WDWPR`, `TR15WV5`, `TR15MV5`, `RG20KN`, `RG20WN`, `RG20VN`, `RD22GSG`, `DUE6BGL2E`, `DUE6BGE`, `Z330MEEF11`. 이 파일의 상세 사양 근거가 빈 것이며, 다른 B30 사실에 해당 모델 정보가 전혀 없다는 뜻은 아니다. 사양 근거가 있는 42개 중 일부 필드가 `null`인 제품은 16개다. 누락된 기능을 '없음'으로 바꾸지 않는다.

대표 38종 모두 선택 핵심 자료의 존재 완료 표시가 있지만, `all_information_complete=false`다. 제품별 색인의 부품 coverage는 34종이 정확 부품번호 미확정, 4종이 선택 호환 기록만 있는 상태이며 전체 BOM 완료 표시는 0종이다. 이 coverage 문구는 색인의 정리 상태로 읽어야 하며, 색인 외의 모든 부품 기록이 없다고 확대 해석하지 않는다.

| 합계 | 1,542 | 실행 승인과 별도로 관리 |

품목별로는 세탁기 520건, 건조기 274건, 냉장고 360건, 식기세척기 388건이다. 검색 topic은 `MANUAL` 1,345건, `SAFETY` 108건, `WARRANTY` 54건, `SERVICE` 35건이다. 정보 묶음과 topic은 다른 분류이므로 수량이 일치할 필요는 없다.

1,542건의 ID 중복·래퍼 ID 불일치·HTTPS 출처 형식 누락·기준일 파싱 오류는 찾지 못했다. 52개 로컬 모델의 대표/공통 코드 참조도 확인했다. 현재 `knowledge.json`의 SHA-256은 manifest와 일치한다.

```text
데이터 버전: B30-COST-V3-20261013-R2
knowledge SHA-256:
5ec8d44ffb4828d54a273ebef0ac1cfd302c1f2415769f50ceb978e2d800a07d
```

이 결과는 구조적 검수다. HTTPS URL이 있다는 사실만으로 원문 내용·현재 요금·사용자 기기에 대한 적용이 검증된 것은 아니다. Drive의 전체 원본 파일을 raw bytes로 다시 내려받아 체크섬 목록 전체를 재검증하지는 않았다.

| 실제 수리용 부품의 가격·공임·총액 | 현재 근거 부족 | `estimate_repair_cost` | 별도 비용 자료와 호환·작업 난이도 연결 필요; 제품 정보 파일만으로 산정 불가 |
| QA·출처 충돌·제외 모델·보완 절차 | 검토·차단용 | 검색 필터·실행 승인·근거 검사 | 일반 해결 방법과 분리하고 제외/금지 조건을 우선 적용 |
| 공식 접수·서비스 경로 | 현재 활용 가능 | F-11, `prepare_service_handoff` | 링크 제공과 예약 접수는 구분; 방문 가능 지역·운영시간은 별도 검증 |
| 색상·치수·무게·에너지등급·판매 순위 | MVP 우선순위 낮음 | 제품 식별 보조·개발 참고 | 실제 증상 판단과 관계있는 필드만 사용; 전국 판매량/고장률 근거로 전용 금지 |

전체 자료를 한 프롬프트에 넣기보다 제품 식별 자료, 답변 근거, 실행 승인 계획, 차단/충돌 정책, 비용 표를 역할별로 연결하는 것이 적합하다. B30에 원문이 있다는 이유로 매뉴얼·보증·부품·금액을 모두 하나의 '검증 완료 답변'으로 취급하지 않는다.

## 4. 주요 파일을 활용하는 구체적인 방법

### 4.1 `products`·`lookup`·`representatives`: 제품 식별

이 파일들은 가장 먼저 사용할 수 있다. 사용자가 선택한 품목과 등록한 모델이 맞는지 확인하고, 정확한 지원 페이지와 설명서로 연결한다. `FX24ENER`는 공통 자료를 `FX24KNTR`로 조회할 수 있지만, 실제 판매 코드와 부품 확인에는 `FX24ENER`를 보존한다. `DUE6BGL2`와 `DUE6BGL2E`는 구분한다.

`query_B30.py`는 전체 코드의 정확 매칭만 하며 모르는 SKU 접미사를 제거하지 않는다. `RD21ESE.AKOR` 같은 생산 SKU와 판매 코드 조회는 별도 절차다. 부품 호환을 확인할 때 이 SKU를 삭제해서 단순 매칭으로 바꾸면 안 된다.

현재 [models.json](../../backend/src/main/resources/homecare/models.json)은 조회표 역할이다. 용량·치수·조작 방식 등 `products_B30.json`의 사양 대부분을 포함하지 않는다. 제품 카드에 상세 사양을 보여 주거나 AI의 기능 가지 선택에 쓰려면 필드별 출처를 유지한 별도 제품 사양 구조가 필요하다.

### 4.2 `knowledge_effective`·`information_index`: 오류·증상·조치 후보

사용할 때는 `record`뿐 아니라 `current_QA_review`, `latest_applicability_update`, `effective_model_lists`, `procedure_supplements`, `use_policy`를 함께 읽는다. 제품별 색인의 후보·충돌·직접 부품 연결을 시작점으로 삼고 실제 사실 ID의 원문 조건을 확인한다.

현재 원문 1,659건의 ID는 중복이 없었고, 검사한 제품별 색인의 후보·직접 참조 목록도 원본 사실 ID에 연결됐다. 그러나 자료의 후보 색인과 현재 런타임은 다르다. 현재 [SearchKnowledgeTool.java](../../backend/src/main/java/com/project/backend/mcp/tool/handler/SearchKnowledgeTool.java)의 `execute()`는 생성 파일의 `modelCodes`와 키워드를 사용하며 B30 전체 색인의 제약을 직접 해석하지 않는다.

자가조치 후보에는 `steps`가 있는 로컬 레코드 283건이 있지만, 단계가 있다는 사실과 실행 승인은 다르다. 로컬 `actionApproved=true`는 0건이고 [approved-plans.json](../../backend/src/main/resources/homecare/approved-plans.json)도 0건이다. 따라서 현재 바로 제공할 수 있는 것은 원문 후보와 제한 사항이며, 승인된 단계형 자가검진 자료는 따로 만들어야 한다.

### 4.3 `review_links`·충돌 자료: 잘못된 안내 차단

이 자료는 삭제할 잡음이 아니라 중요한 제한 근거다. 같은 설명서에 등장한 다른 기능, 타 모델의 해동 버튼, 확인되지 않은 필터 방향·버튼 표기·부품 리비전을 막는 데 사용한다.

예를 들어 `B29-RD21ESE-part-label-conflict`는 외부 필터 페이지의 서로 다른 SKU 표기를 근거로 해당 호환을 미승인으로 남긴다. `B28-MFL71995305-raw-lcd-code-review`는 화면 표기 충돌을 관리한다. 이미 '미확인으로 정리 완료'된 항목을 '문제가 해결돼 사용 승인'으로 바꾸지 않는다.

## 5. 검수에서 발견한 현재 연결 문제

아래는 자료·코드 대조에서 확인한 현상이다. 실제 모델이 잘못된 행동을 지시한 실행 결과와는 구분한다. 이번 보고서에서 수정하지 않았으며 후속 작업의 우선순위를 표시했다.

### R-01 · 김치냉장고 통합 원문 97건이 서비스 검색에서 누락 — 우선

원본 `record.category` 또는 `record.content.category`가 `KIMCHI`인 97건 모두 현재 `knowledge.json`에 없었다. 전체 누락 117건 중 97건이다. 반면 로컬 `models.json`에는 김치냉장고 판매 코드 5개가 남아 있다.

누락에는 `B15-MFL67704818-safety`, `B22-MFL67704818-displayed-error-service-rule`, `B23-MFL69666920-displayed-error-service-rule`, `B24-MFL69666920-physical-cleaning-electrical-safety` 등이 있다. 일부 구형 CSV 사실은 `REFRIGERATOR` 품목으로 들어 있어 김치냉장고 자료가 전혀 없는 것은 아니다. 하지만 최신 통합 원문의 안전·서비스·보증·절차 보완이 모두 연결된 상태는 아니다.

부품 기록 `B26-MFL69666920-part-4756JA3001H`와 `B26-MFL69666920-part-MCS62101823`도 빠져 있다. 이는 프로젝트가 포함하는 제품 유형의 자료이므로 누락 이유와 적용 조건을 재검수할 필요가 있다.

**보완:** 앱 품목은 `REFRIGERATOR`, 제품 하위 유형은 `KIMCHI`로 보존하는 명시적 변환을 두고, 97건을 조건별로 재검수해 연결한다. 현상은 ID 대조로 확인했지만 자료 생성기의 실행 기록이 없어 누락 원인을 확정하지는 않았다. 일반 냉장고와 김치냉장고의 조치·오류·보증을 서로 전용하지 않는다.

### R-02 · 제외 모델을 검색에 허용하는 메타데이터가 있음 — 우선

현재 `modelCodes`와 래퍼의 `effective_model_lists.excluded_model_codes`가 겹치는 레코드는 5건이다.

| 사실 ID | 잘못 일반 후보로 해석할 수 있는 모델 |
|---|---|
| `B19-MFL05882501-topic_37-procedure` | `G646GBB021`, `G646GBB031` |
| `B24-MFL71831233-topic_45-block-13` | `TR15MV5`, `TR15WV5` |
| `B25-MFL71401557-craft-ice-pump-exclusion` | `T876MEE1H1` |
| `B27-QA-20151819274292` | 해당 래퍼에 적힌 건조기 제외 코드 13개 |
| `B27-QA-20150667086592` | `TR15MV5`, `TR15WV5` |

`knowledge()`의 품목·모델 필터와 키워드 점수를 오프라인 재현하면, 모델 `G646GBB021`에 검색어 `정수 필터`를 넣었을 때 첫 번째 레코드가 유일한 상위 후보로 나온다. 이 레코드의 원문은 그 모델의 자가조치·필터 구매 안내로 사용하지 말라는 제한을 가진다.

모델 `TR15WV5`에 `배수필터 마개`를 검색하면 `B21-QA-20150667086592`, `B27-QA-20150667086592`가 후보가 된다. 첫 항목은 모델 목록이 비어 있어 품목 공통처럼 통과하고, 두 번째는 모델 목록에 제외 코드가 들어 있다. 둘 다 원문에서 해당 모델을 제외한다.

**보완:** 제외 목록을 먼저 적용하고 승인/조건부/미확인 모델을 별도 필드로 둔다. 제외 이유를 설명할 자료는 '제약 설명' 용도로만 사용한다. 현재 결과의 `is_action_approved=false`와 빈 승인 계획은 즉시 실행을 막는 장치이지만, 검색 결과 자체가 정확한 모델에 적용된다는 보장은 되지 않는다. 이 재현은 HTTP·LLM 통합 실행 시험이 아니다.

### R-03 · 공통 범위와 미확인 범위가 모델 코드로 잘못 표현됨 — 우선

현재 모델 조회표에 없는 토큰을 `modelCodes`에 넣은 레코드는 48건이다. 토큰은 품목명 5개 항목과 `품목 공통` 43개 항목이다. 실제 등록 모델과 교집합을 검사하는 현재 코드에서는 이런 항목을 찾지 못할 수 있다.

예를 들어 `T5-001`은 보증·유상 조건의 참고 사실이지만 `modelCodes=["품목 공통"]`이어서 정확 모델 검색을 통과하지 못한다. `T1-001`도 `modelCodes=["WASHER"]`이므로 모델 조회용 코드와 품목을 혼용한다.

반대로 `modelCodes=[]`인 QA 검토 항목 8건은 모든 같은 품목의 모델에서 검색될 수 있다. 일부는 적용 미판정 또는 제외 조건을 담고 있어 공란을 '모든 모델 적용'으로 해석하면 안 된다.

**보완:** `scopeType=EXACT_MODEL/CATEGORY_COMMON/CONDITIONAL/UNVERIFIED` 같은 내부 구분을 제안한다. 공통 자료는 정말 공통인 필드만, 적용 미판정 자료는 검토/확인 안내로만 사용한다. 이 구분은 프로젝트 제안이며 현재 표준 MCP 필드가 아니다.

### R-04 · 39건의 적용 미확인 오류 자료와 구조별 검증 플래그 차이 — 우선

원문에 `runtime_eligible=false`가 명시된 39건의 `T2_error_codes`도 현재 생성 파일에 포함돼 있다. 예: `T2-028`~`T2-033`. 현재 이들은 주로 `품목 공통` 범위로 들어 있어 검색되지 않는 문제가 함께 있다. 공통 범위 검색만 수정하면 그동안 검색되지 않던 미승인 자료까지 노출될 수 있다.

또한 `runtime_eligible` 필드가 없는 행은 1,096건이다. 이들은 다른 B30 스키마를 사용하므로 필드가 없다는 이유만으로 부실 자료라고 판단할 수 없다. 반대로 필드 공란을 자동으로 `true`로 보완해서도 안 된다.

**보완:** 자료 형식별 `verification_status`, `answer_use`, `model_application_verified`, 적용표·현재 QA·사용 정책을 해석해 내부 검증 상태를 정규화한다. 미확인 오류의 뜻·원인·조작 방법을 특정 모델의 확정 사실로 노출하지 않는다.

### R-05 · 구조화된 조건 칸이 원문 제한을 모두 담지 못함 — 우선

`record.preconditions`, `warnings`, `applicability_conditions` 중 하나 이상이 있는데 바깥 `conditions=[]`인 행은 24건이다. 예: `B17-MFL71964311-topic_43-procedure`, `B19-MFL05882501-topic_37-procedure`.

원문 제한은 `text` JSON 안에 남아 있으므로 원문이 삭제됐다는 뜻은 아니다. 그러나 서버와 화면이 구조화된 `conditions`만 참조하면 제한을 놓칠 수 있다. 현재 `ToolResults.jsx`의 승인 단계 UI는 `step.caution`을 표시하므로, 승인 계획을 만들 때 원문 주의사항을 실제로 이 필드에 옮기는지 확인해야 한다.

**보완:** 원문 안전·설치·그림·앱 등록·부품 조건을 승인 계획의 필수 전제와 단계별 주의사항에 연결하고, 조치 안내 전 서버가 검사한다. 단순 문장 축약이나 배열 공란 때문에 안전 조건을 소거하지 않는다.

### R-06 · 증상-부품 매핑과 실물 부품-가격 연결이 없음 — 핵심 기능 보완

현재 [parts.json](../../backend/src/main/resources/homecare/parts.json)의 32개 비용 그룹에는 `targetCodes`가 들어 있는 행이 0건이다. `get_repair_candidates`의 매핑은 이 필드를 사용하므로 현재 자료에서는 매핑 경로를 사용할 수 없다. 매핑 시험 fixture와 실제 운영 자료는 다르다.

비용 그룹에는 실제 제조사 부품번호·생산 SKU 호환·B30 사실 ID 연결도 없다. `W01`은 배수펌프 비용 그룹이며, `383EER2001A` 같은 실물 부품번호와 동일한 것이 아니다. 특히 거름망을 배수펌프 전체 교체 가격에 연결하면 잘못된 후보·금액을 만들 수 있다.

**보완:** 오류/증상→검토된 원인 그룹→확인 가능한 실물 부품→가격 출처의 연결을 별도로 만든다. B30의 '가능한 원인'을 고장 확정 또는 교체 필요성으로 승격하지 않는다. 현재 모델의 선택과 확신도 0.5 조건은 그 연결의 정확성을 보장하지 않는다.

### R-07 · 근거 유형·단일 링크가 정보 성격을 단순화함 — 보완

`knowledge()`는 모든 후보의 근거 유형을 `OFFICIAL_MANUAL`로 만들고 `sourceUrls`의 첫 링크만 대표 근거로 쓴다. 실제 자료에는 제품 스펙 페이지, 공식 지원 글, 부품몰, 정책·비교 근거, 충돌 검토가 섞여 있다. 모든 내용을 설명서 직접 근거로 표시하면 사용자가 근거의 성격을 오해할 수 있다.

**보완:** 실제 출처 유형과 필드별 출처·위치를 보존한다. 충돌의 양쪽 출처나 현재 QA의 제한을 한 링크로 축약하지 않는다. 모든 금액과 보증기간에는 해당 필드의 적용 근거를 연결한다.

### R-08 · 승인 계획·후기·개인 적용 자료가 없음 — 준비 상태 구분

현재 승인 계획 0건, 수리 후기 원문 0건이다. B30에서 사용자 제품의 구매일·영수증·생산 리비전·실제 고장 부품·사용 과실을 얻을 수도 없다. 이 값들은 사용자 확인과 엔지니어 진단의 입력이다.

**보완:** 승인 계획은 모델 하나·오류 하나부터 검수해 만들고, 후기 자료는 `REFERENCE/VALIDATION`으로 분리한다. 개인 조건 미확인은 추가 확인으로 표시한다. 제품 정보 파일을 읽었다고 개인 보증/비용/조치가 모두 확정된 것으로 설명하지 않는다.
