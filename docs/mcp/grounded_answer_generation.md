## 1. 정상 답변 경로

### 1.1 호출 구조

- 기존 `AgentChatService`의 모델 호출: MCP 도구 선택 담당
- 도구 선택 모델이 임의로 쓴 최종 문장은 그대로 사용하지 않음
- 최종 답변: 도구 선택과 정책 보완 호출이 끝난 뒤 별도 `GroundedAnswerGenerator` 호출로 구성

```text
상담 상태·위험 확인
 → MCP 도구 선택·조회
 → AnswerContext에서 근거와 승인 조건 확인
 → 모델이 문단·연결 문장·fact ID 구성
 → 출력 검증·본문 복원
 → 최종 답변·생성 모드·근거 이력 저장
```

### 1.2 `AnswerContext`의 근거 종류

| 종류 | 입력 근거와 역할 |
| --- | --- |
| `CONFIRMED` | 서버가 저장한 증상 코드·발생 시점 등 확인한 상담 사실 |
| `REFERENCE` | 해당 품목·모델의 제조사 증상 설명, 원인 후보·상황, 적용 조건. 실제 고장 확정과 구분 |
| `MISSING` | 적용 가능한 설명이 없거나 조건 확인이 필요한 정보 |
| `AUTHORITATIVE` | 기존 서버의 비용·보증·모델 조회·서비스·조치 승인 상태 안내. 문장과 수치를 그대로 유지 |

### 1.3 모델 응답 형식

```json
{"paragraphs":[
  {"opening":"확인된 내용부터 말씀드릴게요.","fact_ids":["SYMPTOM"]},
  {"opening":"제조사 자료에는 다음과 같이 설명되어 있어요.","fact_ids":["REFERENCE_2"]},
  {"opening":"","fact_ids":["TOOL_GUIDANCE"]}
]}
```

- `opening`: 허용된 연결 문장 또는 빈 문자열
- `fact_ids`: 현재 확인된 근거 목록
- 정상 답변에 쓰는 모델 결과: 문단, 선택, 연결 문장
- 실제 설명 본문: 검증된 값으로 복원
- 비용·보증·연락처가 포함된 `AUTHORITATIVE` 본문: 최종 생성 모델에 전달하지 않고 서버에서 복원

### 1.4 생성 제한

- 허용하지 않는 것: 자유로운 사실 요약, 금액 재작성, 새 조치 생성
- 초기 개발 형식의 `text`·앵커 응답: 근거 전체의 정확한 인용과 허용 연결 문장만 통과
- 통과하지 않는 것: 부분 인용, 수치 변경, 새 문장

## 2. 근거 검증과 실행 승인

### 2.1 근거 검증

- 상담 버전과 자료 버전 확인
- 근거 ID는 원본·구조화 자료와 도구의 evidence에 모두 있어야 함
- 2단계 검색기의 품목·정확한 모델·대표 모델 공통 자료·제외·조건부 적용 정책 재사용
- 거부 대상: 다른 모델·품목, 미등록 ID, 변조한 적용 상태
- 도구의 `content`를 그대로 신뢰하지 않고 검증된 로컬 구조화 자료로 설명 재구성
- 생성 입력에서 제외: 원본 JSON, 해시, QA 이력
- 일반 설명에 쓰는 필드: 제조사 자료의 `symptoms`, `causes`, `preconditions`, 조건부 분기의 `condition_summary`
- 제외하는 필드: `action_descriptions`, `action_summary`, 기능 확인이 필요한 분기 주장
- 원인 후보와 조건에는 현재 제품의 실제 원인이 확인되지 않았다는 설명 추가
- 설명서 내용이나 모델 목록은 실행 승인으로 바뀌지 않음

### 2.2 실행 승인

- 도구 결과에 실행 단계가 있으면 실제 승인 계획의 품목·등록 모델·증상/오류·단계 전체 값과 대조
- 실행 자료: 여전히 `approved-plans.json=[]`, 이 작업으로 승인 자료를 등록하지 않음
- 문서의 역할 변경·규칙 무시 등 지시: 데이터로 취급
- 최종 생성 호출에는 도구 callback을 전달하지 않음

### 2.3 출력 검사

- 검사 항목: JSON 구조, 문단 수, 허용 연결 문장, 참조 ID, 순서, 중복, 필수 안내 포함 여부
- 제조사 근거가 있으면 최소 하나의 설명 포함
- 서버 도구 안내는 마지막에 포함
- 거부 대상: 앵커 밖의 금액·보증기간·날짜·연락처·모델명·조치·예약 완료·확정 진단
- 서버 계산·보증 판정은 생성 모델로 대체하지 않음

## 3. 위험·실패·시간 제한

### 3.1 위험 안내

- 기존 위험 확인·긴급 안내와 3단계의 확인 질문: 정책 응답 유지
- 관련 안전 문서가 검색되거나 도구가 안전 차단을 반환하면 고정 안내 사용(최종 생성으로 안전 안내를 재배열하지 않음)

### 3.2 생성 상태

- 저장 위치: `tools.answer_generation`(MCP 도구가 아닌 답변 생성 상태)

| 모드·사유 | 동작 |
| --- | --- |
| `MODEL_GROUNDED` | 출력 검증을 통과한 모델 구성으로 답변 |
| `FIXED_FALLBACK` / `VALIDATION_FAILED` | 형식·근거·필수 안내·새 문장 검사 실패, 기존 고정 안내 |
| `GENERATION_ERROR`, `GENERATION_TIMEOUT` | 생성 장애·시간 초과, 기존 고정 안내 |
| `TIME_BUDGET_EXHAUSTED` | 남은 세션 예산 없음. 생성 모델 호출 생략 |
| `INVALID_EVIDENCE` | 상담·자료 버전, 근거·모델·승인 검증 실패 |
| `SAFETY_GUIDANCE_REQUIRED` | 안전 안내를 기존 순서로 유지 |

- 저장 값: mode, reason, fact ID, evidence ID, 생성 시간, 상담 버전, trace ID
- 로그 값: 모드, 사유, 시간만
- 로그에 넣지 않는 것: 고객 원문, 모델 초안, 토큰
- 기존 도구 연결 장애의 `agent_fallback`과 구분

### 3.3 시간 제한

- 생성 대기 한도: `AgentLimits.toolTimeout`(기본 5초)과 기존 `McpGateway.Session`의 남은 예산 중 작은 값
- 생성은 기존 MCP 도구 호출 횟수(기본 5회)를 늘리지 않음
- 위험·메시지 해석의 별도 8초 제한까지 포함한 전체 HTTP 지연을 20초로 보장한다는 뜻은 아님
- 최종 실제 모델 평가의 생성 시간: 평균 약 1,297ms, 최대 3,074ms

## 4. 검증과 재현

### 4.1 자동 검사

- Java 단위 검사 항목: 근거 없는 가격·보증·날짜·연락처·조치·확정 진단·예약 완료·문서 지시·미등록 근거, 필수 안내 누락·변경, 실행 승인 위조, 생성 오류·시간 초과와 예산 소진
- 실제 FastMCP HTTP 통합 검사 항목: 새 구성 응답, 진동 원인 후보, 승인 미확인 유지, 원본 조치 제외, 고정 대체, 자료 부족, 상담 이력 저장
- 최종 자동 검증: Java 총 253개 중 251개 통과·2개 건너뜀, JAR 빌드 성공, 프론트엔드 lint·production build 성공
    - 건너뛴 2개: 별도 MySQL 실행 환경이 필요한 마이그레이션 검사, 실행한 것으로 계산하지 않음
- MCP 도구의 입력·discovery 계약은 변경하지 않음

### 4.2 실제 모델 평가

- 실행 범위: 실제 모델 14개, 검증된 로컬 자료와 합성 상담 상태로 최종 생성만 실행
- 포함 사례: 진동 표현, 다른 모델, 오류, 자료 부족, 미등록 모델, 4품목 보증, 비용표
- 고정 값: 보증은 실제 `WarrantyService`, 비용은 기존 표의 참고 값
- 원래 비용 계산과 FastMCP 전송: 별도 통합·회귀 테스트에서 확인
- 실제 모델의 도구 선택·조회·끝까지 상담을 동시에 평가한 결과는 아님

| 실행 | 결과 | 변경 내용 |
| --- | --- | --- |
| [초기 결과][initial], [진단 초안][diagnostic] | 4/14 | 초기 형식 |
| [기록][composition] | 6/14 | 전체 인용·문단 구성 보완 |
| [기록][manifest] | 10/14 | 필수 근거 목록과 생성 예시 추가 |

- 고정 대체 응답은 모델 생성 성공으로 세지 않음
- 같은 입력으로 개선한 개발 평가이므로 독립적인 품질 보장으로 해석하지 않음

### 4.3 재현

- backend에서 JDK 21 사용
- 통합 검사: 기존 Python 환경의 `HOMECARE_TEST_PYTHON` 지정

```powershell
./gradlew.bat test bootJar --offline --no-daemon
./gradlew.bat evaluateGroundedAnswer --offline --no-daemon
```

- 두 번째 명령: 기존 `.env`의 모델·키로 합성 평가만 실행, 모델 API 사용량 발생, DB나 서버는 기동하지 않음
- 후속 단계: 전체 실제 Agent 평가, 실제 승인 자가조치, 후속 비용 연결은 5·6·8단계
