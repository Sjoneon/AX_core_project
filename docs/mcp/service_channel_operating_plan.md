# A/S 연결과 센터 데이터 운영 설계

작성일: 2026-10-15 (Asia/Seoul). 상태: **1차 구현 반영(로컬 작업본, 커밋 전)**. 반영 내용은 [점검 문서 8절](manufacturer_data_usage_audit.md#8-4절-해결-반영)에 있다. 자체 센터 디렉터리는 미착수다. [B30 사용·등록 정보·답변 점검](manufacturer_data_usage_audit.md)에서 발견한 서비스 연결 문제의 후속 설계다.

## 운영 방향

현재 주력인 냉장고·세탁기 등의 고장 상담에서는 **공식 출장 접수 연결을 기본으로 제공한다.** 센터 방문이 필요한 경우에만 센터 찾기를 별도로 제공한다. 우선 전국 센터를 직접 운영·동기화하지 않는다.

대치·분당·북수원 3곳이 담긴 `centers.json`을 전국 서비스 조회의 근거로 쓰는 경로는 교체해야 한다. 그렇다고 모든 센터를 소스 코드에 추가하거나, 고객 요청마다 공식 웹사이트를 스크래핑하는 구조로 바꾸지는 않는다. 공식 API·데이터 공급 계약이 없는 현재는 공식 화면으로 인계하는 것이 운영 가능한 기본안이다.

LG [은평센터 안내](https://www.lge.co.kr/support/find-service-center-137)와 [죽전센터 안내](https://www.lge.co.kr/support/find-service-center-255)는 냉장고·세탁기 등 대형 제품에 출장 서비스를 안내한다. 센터별 취급 품목도 다르다. 가까운 건물의 주소를 알려 주는 것과 해당 제품을 그곳으로 가져가 수리받을 수 있다는 것은 다르다. 건조기·식기세척기까지 동일한 내방 규칙을 추정하지 않고 해당 품목의 공식 서비스 안내를 확인한다.

공식 [출장 예약 화면](https://www.lge.co.kr/support/service-engineer-reservation)은 제품·증상·신청자·주소와 일정 확인 과정을 제공한다. HomeCare는 모델·증상·확인 이력을 요약하고 사용자를 이 경로로 연결한다. 현재 앱이 예약을 접수하거나 기사·방문 시간을 배정하는 기능으로 표현하지 않는다.

## 현재 문제는 세 가지다

| 구분 | 현행 상태 | 실무상 문제 |
|---|---|---|
| 데이터 범위 | 패키지 센터 3곳 | 전국 검색으로 해석되며 지역이 다르면 빈 결과가 발생 |
| 입력 연결 | 일반 제품 등록의 `address`와 센터 도구의 `deliverySido/deliverySigungu`가 분리 | 주소가 있어도 지역을 모르는 상태로 조회 |
| 결과 의미 | `fallback_level=NONE`, 빈 목록이어도 상태 `OK`와 “조회 완료” 카드 | 지역 미입력·자료 부족·실제 검색 결과 없음이 구분되지 않음 |

제주 사례는 현재 데이터에 제주 센터가 없는 데다 일반 신규 등록의 지역 필드도 비어 있어, 단순히 센터 수를 늘려서는 해결되지 않는다. 사용자에게 “등록 지역에 센터가 없습니다”라고 단정할 근거가 없다.

## 1차 구현 범위

### 접수 채널과 센터 검색을 나눈다

출장 접수, 전화 상담, 센터 방문 안내를 각각 명시한다. 냉각 문제를 처음 질문했을 때는 증상 설명·필요한 확인 질문을 먼저 제공한다. 사용자가 수리·접수를 요청하거나 적절한 설명 후에도 점검이 필요할 때 공식 출장 접수 버튼을 주된 행동으로 보여 준다. 모든 턴에서 보증·센터·요약 카드를 자동으로 펼치지 않는다.

공식 연결 URL·대표 전화번호·제조사와 확인일은 설정 자료로 관리한다. URL과 전화번호 자체를 설정에 두는 것은 센터 3곳을 전국 조회 결과처럼 쓰는 것과 다른 문제다. 연결 경로에는 허용된 공식 호스트를 쓰고 주기적으로 링크 상태를 점검한다. 공식 홈페이지 내부에서 쓰는 비공개 요청 경로나 임의의 주소·모델 쿼리 인자를 공개 API처럼 이용하지 않는다.

현재 9개 MCP 도구 중 `find_service_centers`가 이 경로를 담당하므로 입력·출력 계약과 소비 화면을 함께 개정해야 한다. 이름만 유지한 채 출장 예약이 완료됐다는 전혀 다른 의미를 반환하면 안 된다. 호환이 필요한 기존 결과와 새 응답은 계약 버전·조회 모드로 구분하고 저장 이력도 처리한다.

센터 데이터 공급이 없는 경우의 목표 응답 예시는 다음과 같다. 새 계약의 설계안이며 현재 구현 값은 아니다.

```json
{
  "status": "EXTERNAL_LOOKUP_REQUIRED",
  "data": {
    "service_mode": "ON_SITE",
    "directory_status": "NOT_INTEGRATED",
    "region_status": "KNOWN",
    "region": {"sido": "제주", "sigungu": "제주시"},
    "centers": [],
    "channels": {
      "onsite_booking_url": "https://www.lge.co.kr/support/service-engineer-reservation",
      "center_finder_url": "https://www.lge.co.kr/support/find-service-center",
      "phone": "1544-7777"
    },
    "booking_status": "NOT_SUBMITTED"
  }
}
```

이때 화면 문구는 “센터 조회 완료, 등록된 센터 없음”이 아니라 “냉장고 점검은 LG 공식 출장 접수로 이어갈 수 있습니다”와 공식 연결 버튼이다. 센터 방문을 원하면 공식 센터 찾기를 별도로 연다. 주소를 공식 페이지에 자동 전송하거나 사용자 대신 접수하지 않는다. 미지원 자동 입력을 약속하지 않고 모델·증상 요약 복사를 제공한다.

### 등록 주소 연결을 바로잡는다

주소 검색 결과에서 기본 주소·상세 주소뿐 아니라 시·도·시·군·구의 정규화된 값과 가능하면 행정구역 식별자도 받는다. 도로명 주소 문자열과 정규 지역 정보를 같은 등록 경로로 저장한다. 수동 입력·기존 데이터에서 지역을 확정할 수 없으면 `REGION_REQUIRED`로 구분해 한 번 확인한다.

기존 `deliverySido/deliverySigungu`를 유지할지 새 지역 필드를 쓸지는 DB 변경 범위와 함께 정한다. 화면의 “설치 주소”와 조회에 쓰는 “배송 지역”의 의미도 통일해야 한다. 주소 문자열을 임의로 쪼개 빈 필드를 채우고 성공 처리하지 않는다. 기존 행의 보정은 확인 가능한 주소 변환과 별도 마이그레이션·검증으로 수행한다.

### 3개 센터 자료의 역할을 제한한다

운영 검색에서는 `centers.json`의 3곳을 기본 조회 소스로 사용하지 않는다. 필요하면 테스트 고정 자료로 분리한다. `ToolDataCatalog`의 필수 파일·매니페스트·해시 검사·센터 도구·계약·화면·회귀 테스트가 이 파일에 연결돼 있으므로 파일만 삭제해서는 안 된다. 다른 제조사로 확장할 때도 채널 제공자와 센터 디렉터리 제공자를 분리한다.

## 자체 센터 목록이 제품 요구사항이 된다면

센터 이름·위치·취급 품목을 앱 안에서 보여 주는 것이 필수라면, 먼저 공식 제휴 API 또는 운영 가능한 승인된 데이터 공급 경로를 확보한다. 이번 공식 페이지 확인과 검색에서는 이 앱이 사용할 공개 센터 조회 API 계약을 확인하지 못했다. 이는 그런 API가 존재하지 않는다는 단정은 아니다. 웹 화면이 내부적으로 JSON을 받는다는 이유만으로 연동 계약이 확보된 것으로 보지 않는다.

공급 경로가 확보된 뒤에는 **지역별 소량 호출만 할지, 제공 목록을 주기적으로 동기화할지**를 제공자의 계약·갱신 정책에 맞춘다. 전체 목록을 안정적으로 받을 수 있다면 백그라운드 작업으로 동기화한 자체 DB를 조회하는 편이 매 채팅마다 전국을 다시 수집하는 것보다 적합하다. 이 경우 전국 센터는 운영 데이터이며 코드 안의 상수가 아니다.

필수 관리 항목은 다음과 같다.

- 제공자·외부 센터 ID·공식 상세 URL, 정규 지역, 주소·좌표, 서비스 방식과 취급 품목, 운영 상태, 출처 확인일.
- `source_updated_at`, `fetched_at`, 마지막 성공 동기화와 실패 상태. 데이터 갱신 주기는 공급 조건을 확인해 정하고 사용자에게 최근 확인일을 표시한다.
- 검증 후 전체 스냅샷 교체 또는 변경분 적용. 일부 수집 실패·행 수 급감으로 전국 목록을 빈 목록으로 덮어쓰지 않는다. 이전 정상본 보존과 되돌리기 경로를 둔다.
- 삭제·이전·휴무·운영시간 변경을 반영하고 조회 실패·자료 만료·지역 미확인·유효한 검색의 결과 없음을 구분한다.
- 지역·제품·서비스 방식으로 조회한다. 좌표와 거리 계산을 구현한 경우에만 거리순이라고 표시하며, 가장 가까운 센터가 출장 배정 담당 센터라고 추정하지 않는다.
- 제공자 인증정보는 서버에서 관리한다. 외부 오류에는 제한된 재시도·타임아웃을 적용하고 이전 자료의 사용 여부·확인 시각 또는 공식 조회 연결을 반환한다. 공급 API가 없을 때 구현이 계속 실패하는 호출을 고객 요청마다 반복하지 않는다.

검색 요청별 결과를 짧게 캐시하는 기능은 이 공급 경로가 확보된 뒤의 최적화다. 캐시를 두는 것만으로 원천 데이터의 범위·이용 가능성·갱신 문제가 해결되지는 않는다. 공식 예약 가능 시간은 단순 센터 주소 정보와도 다르므로 별도 예약 연동 계약 없이 계산·확정하지 않는다.

## 완료 기준

| 검증 사례 | 기대 결과 |
|---|---|
| S836MEE022·제주·냉각 약화, 첫 질문 | 질문에 대한 설명·필요한 확인 질문 우선. 센터가 없다는 단정과 불필요한 전체 카드 나열 없음 |
| 같은 제품의 출장 수리 요청 | 공식 출장 접수 연결·모델/증상 요약·아직 접수하지 않았음 표시 |
| 수도권 신규 등록과 제주 신규 등록 | 설치 주소와 구조화 지역이 함께 저장되고 수정 후에도 일치 |
| 주소는 있으나 기존 지역 필드 공란 | 필요 시 지역 확인. 빈 지역으로 검색한 뒤 조회 완료로 처리하지 않음 |
| 공급 경로 미연동 / 외부 장애 / 결과 없음 | 서로 다른 응답과 고객 문구. 3개 고정 센터로 조용히 대체하지 않음 |
| 자체 디렉터리가 도입된 경우 | 전국 범위·취급 품목·최근 갱신·장애 복구 검증. 제주를 포함한 수도권 외 사례 검사 |
| 기존 저장 상담 재조회 | 과거 센터 결과를 당시 안내로 표시. 최신 영업·예약 가능 상태로 오인시키지 않음 |

1차 구현에서 출장 연결·주소 연결·응답 상태를 반영했다(DB 스키마는 변경하지 않음). 이 순서로 출장 연결과 주소 연결·응답 상태를 바로잡고, 자체 센터 디렉터리의 사업상 필요와 데이터 공급이 확인되면 별도 작업으로 진행하는 순서다.
